# SmartFactory Twin 智慧工厂数字孪生与 AI 智能分析平台实验方案 V1.0

## 一、实验目的与项目定位

本实验以机械加工工厂为业务场景，以数字孪生为可视化载体，以工业时序数据和 AI 分析为核心能力，构建一个虚拟工厂，将现实工厂中的生产设备、生产线、环境、订单和运行数据映射到数字空间，通过数据处理、三维可视化和 AI 模型，实现工厂运行状态监测、生产数据分析、设备异常检测和故障风险预测。

项目正式定位为：

> **SmartFactory Twin：智慧工厂数字孪生与 AI 智能分析平台 V1.0**

系统围绕五个核心目标展开：

1. 工厂三维数字化；
2. 设备数据实时采集；
3. 生产数据分析；
4. AI 预测与异常检测；
5. 智能化决策辅助。

项目主线概括为：三维数字孪生负责"看得见"，工业时序数据负责"有依据"，AI 模型负责"能分析"，软件工程负责"可运行、可解释、可扩展"。项目按真实软件工程标准分阶段实现，按本科毕业设计、GitHub 作品集及研究生阶段继续扩展的标准规划。

## 二、实验对象：虚拟工厂设定

### （一）工厂拓扑

第一版工厂设定为虚拟机械加工工厂，规模如下：1 个工厂、2 个车间、4 条生产线、12 台生产线核心设备、2 台辅助设备，合计 14 台设备。该规模足够演示，又不会让第一版建模和数据设计过重。

| 层级 | 组成 |
|------|------|
| 工厂 | SmartFactory Twin 虚拟机械加工工厂 |
| 车间 A：机加工车间 | 生产线 A1（CNC-01 数控机床、ROB-01 机械臂、CONV-01 传送带）；生产线 A2（CNC-02、ROB-02、CONV-02） |
| 车间 B：检测与装配车间 | 生产线 B1（CNC-03、ROB-03、INSP-01 自动检测台）；生产线 B2（CNC-04、ROB-04、INSP-02） |
| 辅助设备 | AIR-01 空压机、PUMP-01 冷却泵 |

### （二）核心业务场景

第一版围绕一个机械加工订单流程展开：客户订单 → 生产计划 → 生产线排产 → CNC 加工 → 机械臂上下料 → 传送带运输 → 自动检测 → 合格品入库 / 不合格品记录 → 设备运行数据与生产数据汇总 → AI 异常检测与产量预测。

系统需要回答五个业务问题：

1. 当前工厂哪些设备在运行、停机、告警？
2. 每条生产线的产量、合格率和设备利用率如何？
3. 哪台设备出现异常运行模式？
4. 未来一段时间哪些设备存在较高故障风险？
5. 当前订单能否按计划完成？

## 三、实验环境与技术选型

系统总体架构分为六层：前端展示层（React + Three.js + ECharts，承载 3D 工厂、设备监测、数据分析、AI 助手）、后端业务层（Python + FastAPI + WebSocket，承载用户管理、设备管理、数据接口、告警管理）、数据处理层（Kafka / Python / Pandas）、AI 模型层（Scikit-learn / XGBoost）、数据存储层（PostgreSQL / TimescaleDB / Redis）、数据来源层（模拟传感器 / 公开工业数据集 / IoT 设备）。

第一版技术选型如下，不同时引入太多框架：

| 模块 | 技术 | 作用 |
|------|------|------|
| 前端 | React + TypeScript | 页面和交互 |
| 3D 引擎 | Three.js | 工厂三维场景 |
| 3D 建模 | Blender | 建筑和设备模型 |
| 图表 | ECharts | 数据可视化 |
| 后端 | Python + FastAPI | API 和业务逻辑 |
| 数据库 | PostgreSQL | 业务数据存储 |
| 时序数据 | TimescaleDB | 设备时序数据 |
| 实时通信 | WebSocket | 实时数据推送 |
| 数据处理 | Pandas | 数据清洗和转换 |
| 消息队列 | Kafka | 实时数据流 |
| 机器学习 | Scikit-learn + XGBoost | 异常检测和预测 |
| 部署 | Docker | 环境部署 |

**已确认的四个设计决策**：

| 决策项 | 最终选择 |
|--------|----------|
| 工厂类型 | 机械加工工厂 |
| 三维形式 | React + Three.js 网页 3D（Unity 作为备选，暂不作主线） |
| 数据来源 | 模拟数据为主，公开数据集做模型验证 |
| 开发方式 | 个人独立开发 + AI 辅助，文档驱动，分阶段验收 |

其中 PostgreSQL 和 TimescaleDB 结合使用，TimescaleDB 是 PostgreSQL 的时序数据扩展。第一版三维目标不是"电影级工厂"，而是：工厂厂区可浏览、两个车间可见、四条生产线可见、设备可点击、设备状态颜色可映射、关键设备有简单动画、实时数据能驱动状态变化。

## 四、实验数据设计

### （一）设备时序数据

每台设备产生不同的运行数据。以一台电机为例，数据字段及示例值为：

| 字段 | 示例 | 含义 |
|------|------|------|
| device_id | M001 | 设备编号 |
| temperature | 65.2 | 温度 |
| vibration | 2.5 | 振动值 |
| current | 8.6 | 电流 |
| speed | 1500 | 转速 |
| running_status | RUNNING | 运行状态 |
| timestamp | 时间戳 | 数据采集时间 |

数据每隔 1～3 秒产生一条，形成持续的时序数据流。注意：以上是演示数据字段和示例值，不是具体设备的安全运行标准。

### （二）生产业务数据

| 数据 | 说明 |
|------|------|
| order_id | 订单编号 |
| product_id | 产品编号 |
| planned_quantity | 计划生产数量 |
| actual_quantity | 实际生产数量 |
| qualified_quantity | 合格数量 |
| production_time | 生产时间 |
| production_line_id | 生产线编号 |

基于这些数据可计算：生产完成率、产品合格率（合格数量 ÷ 总生产数量 × 100%）、设备利用率、单位时间产量、设备停机时间。

### （三）数据来源方案

采用组合方案，分阶段推进：

1. **方案 A（第一阶段推荐）：模拟工业传感器数据**。Python 编写模拟程序，模拟设备运行、温度变化、振动变化和异常状态。优点是可控、方便开发、可自主设计业务场景。
2. **方案 B（第二阶段）：公开工业数据集**。使用真实采集的历史数据训练模型，推荐数据源包括 UCI Machine Learning Repository、NASA Intelligent Systems Division、Kaggle Datasets，例如 NASA 的 C-MAPSS 涡扇发动机数据集可用于研究预测性维护和剩余使用寿命估计。
3. **方案 C（可选进阶）：真实物联网设备**。使用传感器和开发板采集真实环境数据，通过 MQTT 上传，属于项目进阶，不是第一阶段的必要条件。

第一版数据流为：Python 模拟器 → FastAPI 数据接入接口 → PostgreSQL / TimescaleDB → WebSocket 推送 → React + Three.js / ECharts → AI 分析服务。Kafka、Redis 第一阶段不强制引入，等系统链路跑通后，再把模拟器到后端的数据接入替换为 Kafka。

## 五、数据模型设计

实验第一阶段确定五张核心数据表：

**1. 设备基础表 devices**：device_id（设备编号，如 CNC-01）、device_name（设备名称）、device_type（CNC / ROBOT / CONVEYOR / INSPECTION / AUX）、workshop_id（所属车间）、line_id（所属生产线）、model（设备型号）、status（RUNNING / IDLE / STOPPED / ALARM / MAINTENANCE）、installed_at（安装时间）、created_at（创建时间）。

**2. 设备时序数据表 device_telemetry**：id（BIGSERIAL 主键）、device_id、temperature（温度）、vibration（振动）、current（电流）、speed（转速）、running_status（运行状态）、timestamp（TIMESTAMPTZ 采集时间）。初期可用 PostgreSQL 普通表，后续迁移为 TimescaleDB hypertable。

**3. 生产订单表 production_orders**：order_id、product_id、planned_quantity（计划数量）、actual_quantity（实际数量）、qualified_quantity（合格数量）、line_id（生产线）、planned_start（计划开始）、planned_end（计划结束）、status（PLANNED / IN_PROGRESS / COMPLETED / DELAYED）。

**4. 告警表 alarms**：alarm_id（BIGSERIAL）、device_id、alarm_type（TEMPERATURE / VIBRATION / CURRENT / STATUS）、alarm_level（INFO / WARNING / CRITICAL）、message（告警说明）、detected_at（检测时间）、resolved_at（解除时间）。

**5. 维护记录表 maintenance_records**：record_id（BIGSERIAL）、device_id、maintenance_type（ROUTINE / REPAIR / INSPECTION）、description（维护说明）、started_at、finished_at、cost（维护成本，可选）。

## 六、AI 模型实验设计

不建议一开始就训练深度学习大模型，先做三个有明确业务意义的模型。

**模型一：设备异常检测（第一优先级）**。目标：判断设备当前的运行数据是否偏离正常模式。设备正常运行时温度处于正常波动范围、振动变化平稳、电流变化符合运行负载；当运行数据出现异常组合时，系统标记为异常并生成告警。技术选择：Isolation Forest、Local Outlier Factor、XGBoost（有可靠标签时）。输出示例：device_id（M001）、anomaly_score（0.92）、status（ANOMALY）、detected_at（时间戳）。异常分数仅用于演示，不代表实际故障概率。

**模型二：设备故障风险预测**。目标：根据历史运行数据和故障记录，预测设备未来一段时间内的故障风险。输入：历史温度、振动变化、电流变化、运行时长、设备历史维护记录。输出：风险等级、预测结果、主要影响特征。可使用 XGBoost、Random Forest；有足够可靠的带标签数据时可训练分类模型。模型输出是辅助维护决策的风险提示，不能直接作为设备停机或继续运行的唯一依据。

**模型三：生产效率预测**。目标：根据历史生产数据预测未来的生产趋势。输入：历史产量、设备运行时间、生产线状态、订单计划、产品类型。输出：未来产量预测、订单完成时间估计、生产效率趋势。算法从 Linear Regression、Random Forest、XGBoost 开始，LSTM 为进阶选项。

三个模型构成处理链：设备与生产历史数据 → 异常检测（发现异常状态）→ 风险预测（评估故障风险）→ 产量预测（预测生产趋势）→ AI 分析结果统一输出 → 数字孪生场景更新 + 告警 + 分析报告。

## 七、系统功能模块与前端页面

系统分成六个核心业务模块：模块一 工厂三维数字孪生（厂区三维场景、车间与生产线展示、设备模型加载、设备点击交互、设备运行状态映射、设备状态动画）；模块二 工业数据采集与监测（设备运行数据、温度/振动/电流等传感器数据、生产数量、设备运行时长、实时数据展示）；模块三 生产数据分析（生产数量统计、设备利用率、生产效率分析、设备停机时间分析、产品合格率统计）；模块四 AI 智能分析（设备异常检测、设备故障风险预测、设备剩余使用寿命估计（进阶）、生产趋势预测）；模块五 设备管理与告警（设备信息管理、设备运行记录、告警记录、告警等级、设备维护记录）；模块六 AI 智能助手（进阶）（自然语言查询设备数据、自动分析设备异常、生成生产分析报告、查询历史运行记录）。

设计原则：三维数字孪生是系统的可视化载体，工业数据是系统的基础，AI 模型是系统的智能分析能力，不要让三维模型成为整个项目的全部。

前端设计为工业监控平台，包含五个页面：页面一 工厂数字孪生总览（三维场景、车间分布、设备运行状态和关键指标）；页面二 设备监控中心（查看温度、振动、电流、转速的实时变化曲线）；页面三 生产数据分析（生产数量、合格率、设备利用率、生产线效率）；页面四 AI 预测分析（异常检测结果、风险趋势、模型预测结果和历史告警）；页面五 AI 工业助手（自然语言查询设备信息、分析异常、生成生产报告）。

### 第一阶段执行顺序

第一阶段目标：不写 Three.js，不接 Kafka，不训练复杂模型，先把虚拟工厂、业务对象、数据模型和需求文档确定下来。建议按以下顺序推进：

1. 初始化 Git 仓库和目录结构（main / develop / feature 分支：feature/backend-data-model、feature/frontend-3d-scene、feature/ml-anomaly-detection）；
2. 编写 docs/requirements.md（含项目背景与定位、业务场景、用户角色与使用场景、系统总体目标、功能需求、非功能需求、虚拟工厂设定、数据字典、系统架构、里程碑与验收标准、风险与边界说明）；
3. 编写 docs/database_design.md；
4. 定义设备清单 CSV/JSON；
5. 定义模拟器输出字段；
6. 搭建 FastAPI 最小后端；
7. 建立 PostgreSQL 表；
8. 用 Python 模拟器写入一条完整数据链路；
9. 用简单 API 查询设备和时序数据；
10. 再进入前端三维阶段。

## 十、风险与边界说明

以下边界必须写清并在实验全程遵守：

- 第一版数据为模拟数据，模拟数据用于系统联调和演示，公开数据集用于模型训练和评估，不能把模拟数据包装成真实工厂数据；
- AI 输出为辅助分析，模型结论定位为辅助决策，不作为真实设备停机依据；
- 三维模型为简化工业场景；
- 系统目标是工程演示和教学研究，不替代真实 MES/SCADA。

重点研究的三个技术问题：工业时序数据处理（大数据专业特色）、设备异常检测与预测性维护（AI 技术特色）、实时数据与三维场景同步（数字孪生核心特色）。

本实验的最终标准：不仅能运行系统，还能独立向别人解释每个模块为什么存在、数据如何流动、模型如何工作，以及整个系统是如何协同的——这比单纯做出一个炫酷的工业大屏重要得多。
